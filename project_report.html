2. Introduction

In modern collegiate engineering education, students in computer science and artificial intelligence disciplines are tasked with managing multiple rigorous courses simultaneously. Each individual academic module demands ongoing engagement across assignments, coding lab deliverables, conceptual exercises, and periodic revision schedules. Without disciplined time allocation, students frequently experience deadline panic and suboptimal preparation.

StudyPlanner CLI is an educational, console-based academic management platform and study optimization engine built from the ground up in native Java (JDK 21+). Developed as part of the Programming in Java curriculum at VIT Bhopal University, StudyPlanner demonstrates the practical application of object-oriented design patterns, multi-tier layered architecture, functional data processing via the Java Stream API, persistent relational storage using SQLite with JDBC PreparedStatements, asynchronous multithreading through ScheduledExecutorService, and robust file handling with Java NIO.2.

Unlike commercial mobile applications that require continuous cloud connectivity, browser rendering, and external tracking feeds, StudyPlanner runs completely within a local operating system terminal. It models the core operations of student academic productivity: course credit structures, dynamic task priority indexing (LOW, MEDIUM, HIGH), automated overdue deadline auditing, conflict-free timetable scheduling, analytical progress computation, and automated disaster-recovery database backups.

3. Problem Statement

When undergraduate students manage academic commitments, task tracking is almost universally executed through fragmented, ad-hoc mechanisms: paper notebooks, chaotic messaging groups, LMS notifications, and transient mobile notes. In such models, the academic workflow suffers from severe deficiencies:

  • No Unified System of Record: Course credits, assignment deliverables, and revision targets are scattered across unrelated media.
  • Absence of Dynamic Overdue Tracking: Static to-do lists do not compute temporal state. When an assignment deadline passes, students receive no automated overdue alerting or urgency re-indexing, resulting in missed submissions.
  • Uncoordinated Revision Scheduling: Students schedule study blocks without checking for temporal overlap or estimated workload, creating timetable conflicts and unrealistic daily targets.
  • Lack of Quantitative Progress Metrics: Students cannot evaluate completion percentages across individual courses, preventing informed reallocation of study hours toward credit-heavy subjects.
  • Absence of Auditable Backups & Portability: Commercial tools demand continuous connectivity and subscription fees. There is an academic need for an authentic, self-contained Java system providing local persistence, automated CSV exports, and point-in-time database snapshot backups.

8. Design Decisions & Rationale

  1. Embedded SQLite via JDBC vs. External Client-Server RDBMS (MySQL/PostgreSQL):
    Rationale: External databases create administrative friction for academic evaluation (user permissions, ports, schema imports). SQLite provides zero-configuration local persistence in data/studyplanner.db with complete ACID transaction guarantees.
  2. Java Stream API vs. Iterative SQL Aggregations:
    Rationale: Progress percentages and workload totals are computed in-memory via Java Streams (groupingBy, filter, mapToInt). This avoids redundant disk I/O and demonstrates modern functional programming idioms.
  3. In-Memory Temporal Interval Logic vs. Database Queries for Conflict Detection:
    Rationale: Interval comparisons ($start_A < end_B \land end_A > start_B$) executed with Java LocalTime provide microsecond precision without SQL date dialect quirks.
  4. ScheduledExecutorService vs. Raw Thread.sleep() Background Threads:
    Rationale: Thread pooling with daemon threads avoids JVM hangs, resource leaks, and guarantees graceful termination via runtime shutdown hooks.
  5. Java NIO.2 (Files & Path) vs. Legacy java.io.File:
    Rationale: Java NIO.2 provides atomic file copies (StandardCopyOption.REPLACE_EXISTING), explicit UTF-8 charset handling, and enhanced performance across operating systems.

9. Implementation Details

9.1 Dynamic Overdue Auditing & Temporal Status Evaluation

The system evaluates whether an academic task is overdue dynamically by validating both its completion state and chronological deadline against the system clock:

public boolean isOverdue() { return status == TaskStatus.PENDING && deadline != null && deadline.isBefore(LocalDate.now()); } public boolean isDueToday() { return status == TaskStatus.PENDING && deadline != null && deadline.isEqual(LocalDate.now()); }

9.2 Functional Progress Analytics via Java Stream API

Subject-specific completion rates are computed cleanly by grouping tasks by subject ID and performing downstream counting:

public Map<String, Double> getSubjectWiseProgress() { List<Task> tasks = taskService.getAllTasks(); if (tasks.isEmpty()) return Collections.emptyMap(); Map<Integer, String> subjectCodeMap = subjectService.getSubjectCodeMap(); // Group tasks by subject ID using Stream API Map<Integer, List<Task>> tasksBySubject = tasks.stream() .collect(Collectors.groupingBy(Task::getSubjectId)); return tasksBySubject.entrySet().stream() .collect(Collectors.toMap( entry -> subjectCodeMap.getOrDefault(entry.getKey(), "SUB-" + entry.getKey()), entry -> { List<Task> subTasks = entry.getValue(); long completed = subTasks.stream() .filter(t -> t.getStatus() == TaskStatus.COMPLETED) .count(); return ((double) completed / subTasks.size()) * 100.0; } )); }

9.3 Timetable Temporal Conflict Detection Algorithm

Validates whether two study sessions on the same date overlap in time:

public boolean conflictsWith(StudySession other) { if (other == null || this.id == other.id) return false; if (this.status == SessionStatus.CANCELLED || other.status == SessionStatus.CANCELLED) return false; if (!Objects.equals(this.sessionDate, other.sessionDate)) return false; // Overlap condition: this.start < other.end AND this.end > other.start return this.startTime.isBefore(other.endTime) && this.endTime.isAfter(other.startTime); }

12. Challenges Faced & Practical Solutions

Building an academic task and timetable management platform in native Java presented several real-world software engineering hurdles. The following challenges were encountered during development and successfully resolved:

Challenge 1: Non-Printable BOM Characters in Standard Input Pipes

When running automated test scripts or piping terminal keystrokes on Windows command prompts, standard input streams occasionally transmitted a Byte Order Mark (BOM, \uFEFF) or control characters on the first keystroke. As a result, exact menu string matches (e.g., choice.equals("6")) failed silently and fell back to default handlers.

Solution: Developed a centralized, defensive readChoice() input sanitizer in Main.java that strips non-printable regex patterns: choice.replaceAll("[\\p{Cntrl}\\uFEFF]", "").trim(), ensuring 100% reliable menu dispatch across interactive and piped terminal streams.

Challenge 2: Inadvertent Overdue Flagging of Completed Historic Tasks

A naive overdue checking condition evaluated solely whether task.getDeadline().isBefore(LocalDate.now()). Consequently, assignments submitted on time weeks earlier were incorrectly flagged as overdue deliverables, distorting student progress analytics.

Solution: Enforced dual-predicate domain validation in Task.java: an overdue condition strictly requires that the task's state remains TaskStatus.PENDING in addition to deadline expiration: status == TaskStatus.PENDING && deadline.isBefore(LocalDate.now()).

Challenge 3: Non-Blocking Real-Time Background Notification Rendering

Surfacing active overdue notifications without blocking user keyboard input or forcing busy-wait loops in the CLI menu loop required careful thread coordination.

Solution: Implemented ScheduledExecutorService with a custom daemon thread factory that periodically audits task states in the background and writes alerts to an AtomicReference<String>. The foreground CLI thread reads this reference in $O(1)$ time upon menu redraws with zero I/O blocking.

Challenge 4: Idempotent Demo Data Seeding Across Repeated Executions

Triggering the sample academic data seeder on a database that had already been partially configured generated SQLite unique constraint violations (UNIQUE constraint failed: subjects.code).

Solution: Re-engineered seedDemoData() to perform an idempotent probe: it first queries for existing subjects by code (e.g. CS101), reusing their primary keys if found, and selectively populates missing tasks and sessions, completely eliminating duplicate key crashes.

Challenge 5: Zero-Configuration Native Java Portability

Requiring academic evaluators to install Maven or configure build paths creates setup obstacles that can hinder evaluation.

Solution: Integrated the maven-shade-plugin into pom.xml to compile a standalone fat JAR (study-planner-cli.jar) bundling the SQLite native drivers. Accompanied by platform launchers (run.bat and run.sh), the application executes instantly on any computer equipped with standard Java 21+.
